## Дополнительно

### Как выглядит “выдача конфига”

1. Клиент логинится → получает JWT
2. Клиент регистрирует устройство (/devices/bind)
3. Клиент просит конфиг (/vpn/config) с параметрами:
    - region / node preference
    - policy_id (или “current”)
4. Сервер:
    - выбирает node по региону + нагрузке
    - создаёт peer/клиента на data-plane (WG: добавить peer; Xray: добавить client)
    - отдаёт клиенту конфиг + метаданные (версия, срок, policy hash)
5. Клиент применяет конфиг локально.

### Политики split tunneling: как хранить и версионировать

- include_apps / exclude_apps (packageName)
- include_domains / exclude_domains (если будет доменная логика)
- default_route = VPN или DIRECT
- версия + хэш
Сервер хранит `policy_version` и отдаёт клиенту. Клиент кэширует и проверяет обновления.

### Безопасность

- TLS везде
- Refresh токены хранить как хэши в БД
- Привязка конфигов к device_id 
- Ротация ключей
- Rate limiting на auth/config endpoints
- Логи аудита: кто, когда, какой конфиг выдал
