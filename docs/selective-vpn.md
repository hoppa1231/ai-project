# Выборочный VPN

По умолчанию трафик идёт напрямую. Пользователь добавляет сайт/IP одной строкой; приложение выбирается отдельной кнопкой из установленных приложений с launcher-activity. Изменения применяются после кнопки «Сохранить» и успешного ответа backend. CIDR /0, DOMAIN_KEYWORD и пользовательские GEOIP запрещены; домены .ru, .su, .рф (включая punycode) сервер отклоняет. IP не проверяется по географии, DNS и CNAME на сервере не разрешаются — это базовая проверка доменной зоны, не геофильтр.

До Telegram-входа приложение использует только Telegram-домены и официальные IP-сети, backend возвращает только эту политику и явно настроенные гостевые узлы. Гость может выбрать только узел из этого списка; регион, посторонний exitNodeId и CASCADE не дают доступа к обычным узлам. При недоступности выбранного гостевого узла backend пробует дефолтный и разрешённые резервные. После Telegram-входа доступны серверы из /nodes (гостевой inbound исключён, обычный inbound того же физического сервера регистрируется отдельным узлом) и редактирование сервисов. Старый гостевой туннель останавливается, локальный конфиг очищается; следующее подключение получает конфиг авторизованного пользователя.

## Развёртывание

1. Применить Flyway V13 (выполняется backend при старте). Миграция переводит политики на DIRECT и удаляет устаревшие пользовательские overrides: DIRECT/BLOCK, keyword/GEOIP и домены российских зон. Сохранить резервную копию БД перед обновлением рабочего сервиса.
2. Подготовить **отдельный inbound Telegram на выбранном сервере**, зарегистрировать его как отдельный узел и задать backend `DEFAULT_VPN_NODE_ID` равным UUID этого узла. Переменная передана в docker-compose.yml; продовый compose читает env_file. Резервные Telegram-only узлы задаются списком UUID через `FALLBACK_GUEST_NODE_IDS` (через запятую). Все они должны иметь такие же серверные ограничения. При недоступности дефолта используются только эти явно разрешённые узлы; если ни один не здоров, выдача запрещена. Обычные узлы никогда не используются как гостевой резерв.
3. На VPN-узле установить правила из `docs/examples/telegram-only-xray-routing.json` перед общими правилами, заменив inboundTag и outboundTag на реальные теги. Это фрагмент для существующего Xray-конфига, не полный конфиг. Он разрешает официальные Telegram IP и TCP DNS к 1.1.1.1:53, затем блокирует остальное на гостевом inbound. Не использовать этот inbound для обычного полного доступа. По доменным именам разрешение здесь намеренно не выдаётся: клиент может подделать имя назначения.
4. Пересобрать и установить Android-приложение; проверить запуск до авторизации, недоступность других сайтов через гостевые реквизиты, вход Telegram, новое подключение, выбор сервера, DNS и добавление сервиса/приложения.

**Без шага 3 ограничения Android не защищают от изменённого клиента.** Гостевые реквизиты, выданные до обновления на других inbound, нужно отозвать отдельно. Код не изменяет настройки рабочих VPN-узлов автоматически. На fin ограничения Xray и Android-туннель проверены 2026-11-08; результаты ниже.

Базовый набор: Telegram, YouTube, Discord, Meta, X/Twitter, Signal, LinkedIn, Medium и ряд медиа. Это стартовый список, не полный реестр блокировок и не утверждение об одинаковой доступности во всех сетях. Большой IP-список ru-blocked не загружается автоматически: он способен захватывать общие адреса хостинга и расширять проксирование за пределы выбранных сервисов.

Официальные Telegram CIDR: https://core.telegram.org/resources/cidr.txt (сверены 2026-11-08). Поддерживать синхронно Android fallback, миграции/правила backend и Xray allowlist при будущих обновлениях.

Оптимизация в рамках этого изменения: устранено применение несохранённого черновика и двойной перезапуск при сохранении; индексы строк вычисляются один раз на список; приложения загружаются вне UI-потока по открытию диалога; убрана отдельная загрузка Telegram inventory вместо обычного bootstrap. Численные улучшения потребления CPU/RAM/батареи не измерялись.

## Добавление из браузера через «Поделиться»

В браузере: «Поделиться» → наше приложение → проверить домен/IP → «Добавить». До авторизации диалог предлагает вход через Telegram; после входа требуется отдельное подтверждение добавления.

Обрабатываются ACTION_SEND с text/plain и EXTRA_TEXT при холодном запуске и через onNewIntent. В тексте ищется HTTP(S)-ссылка; путь, query, fragment и порт в правило не включаются. Домен нормализуется через IDN и превращается в DOMAIN_SUFFIX для конкретного host и его поддоменов (не происходит угадывания корневого домена). IPv4/IPv6 превращаются в /32 и /128. Ссылки с credentials, неправильными адресами/портами, несколько разных сайтов и российские зоны отклоняются. Скрытые redirect/короткие ссылки не раскрываются по сети; добавляется домен из присланной ссылки.

До подтверждения серверных изменений нет. После подтверждения правило сохраняется тем же PUT /policy/current с серверной проверкой. Если сайт уже покрыт включённым правилом, дубликат не создаётся. Отключённое редактируемое правило с тем же значением включается. При наличии несохранённого черновика диалог явно предупреждает, что подтверждение сохранит и его. При ошибке сервера диалог остаётся с ошибкой и возможностью повторить попытку. Успешное изменение применяется к активному туннелю; если запуск не удался, пользователь видит просьбу переподключиться. Полный исходный URL в Bundle/правило не сохраняется: для восстановления диалога используются только нормализованные destination и matchType.

Проверки 2026-11-08: 6 JVM-тестов SharedWebsiteParserTest прошли при отдельной компиляции парсера и тестов Kotlin compiler 2.2.10 + JUnit 4.13.2 из локального кеша (без Android Gradle). Manifest XML/intent-filter и git diff --check прошли. Это не сборка APK и не проверка sharesheet/Compose/сервера на устройстве. Позднее полная Android-сборка и JVM-тесты успешно завершены; см. актуальную проверку ниже.

## Проверка fin 2026-11-08

Backend selective-v14 развёрнут на moscow после резервного копирования БД. V14 меняет уникальность node-agent endpoint на endpoint + inboundTag. Исправлено чтение nullable telegram_id через boxed Long: primitive превращал SQL NULL в 0 и ошибочно открывал гостю полный сценарий. Regression-тест включён в успешный backend test/installDist.

На fin работают отдельные inbound 446 (Telegram guest) и 447 (обычный), оба зарегистрированы в backend. DEFAULT_VPN_NODE_ID указывает на гостевой; агент 9090 ограничен firewall. В production routing tag блокировки называется blocked.

Android APK установлен с сохранением данных. FinNodeDeviceSmokeTest прошёл: гостевой запрос другой ноды/CASCADE возвращает SINGLE fin:446, Telegram HTTP отвечает, непроксируемый ipify использует egress телефона, принудительно проксируемый example.com отклоняется сервером. После перезапуска UI показывает FINLAND · TELEGRAM и НА СВЯЗИ. Проверен SEND example.com с подтверждением и гостевым входом; .ru отклоняется. Реальный Telegram-вход, сообщения/звонки, обычный inbound с телефона и авторизованное сохранение Share не проверялись.

## Индикаторы и вход (2026-11-08)

На главной странице вместо квоты три индикатора с отдельными HTTPS HEAD-проверками: российский ya.ru, зарубежный example.com, заблокированный api.telegram.org. Это представители групп, а не реестр доступности всех сайтов. Цвета: зелёный — получен HTTP 2xx/3xx, красный — нет успешного ответа за таймаут, приглушённый — ещё не проверено/подключение меняется. Нажатие повторяет проверку, автоматический интервал — 60 секунд, запросы вне UI-потока. Используется фактическая маршрутизация устройства, поэтому выключенный ВПН не подменяет результат искусственным красным. Пауза/подключение сбрасывают результат.

Вход из приложения сначала POST /auth/telegram/app-login/start, затем tg://resolve на бота (t.me fallback при отсутствии обработчика), опрос challenge каждые 2.5 секунды до 5 минут. Подтверждение /start выполняет пользователь. Гостевой конфиг/кеш политики очищаются при READY. Веб-страница остаётся резервным входом и содержит напоминание открыть её с включённым ВПН.

По решению пользователя трафиковые лимиты отключены: TRAFFIC_LIMITS_ENABLED=false по умолчанию, выдача не отклоняется при исчерпанной квоте, node-agent получает totalBytes=0 (безлимит). Учёт сохраняется. Квота API содержит limitsEnabled; TTL конфигурации и Telegram-only ограничения гостя остаются отдельными механизмами. Перед повторным включением лимитов требуется отдельная миграция действующих клиентов и согласование UI.

Обновление индикаторов: исходные PNG без видимых подписей, стеклянные лампы; Google generate_204 и ChatGPT вместо example.com/Telegram, период10сек только RESUMED экрана. HTTP403/429 показываются нейтрально как ограниченная проверка, детали остаются в accessibility. По UI-проверке на телефоне Google/ya.ru доступны, ChatGPT отвечает403; это не подтверждение доступа к чату.

После ответа403 у ChatGPT третий индикатор переведён на статический Discord robots.txt, интервал10сек сохранён.
